**普通支付**：用户每次付款都在微信小程序内确认一次。适用于一次性商品订单、单次服务等按笔结算的业务。用户签约一次后由商户直接扣款的场景（定期配送、订阅制等）请改用[微信小程序支付 V3（免密支付）](/cases/wechatpay-mini-v3-recurring)。

<Callout type="warn">
使用本指南前，请联系 stera smart one 开通微信小程序支付 V3 并确认应用具备联调条件。
</Callout>

## 1. 接入前准备

{/* prettier-ignore */}
| 项目 | 商户需要准备的内容 |
|---|---|
| 微信小程序 | 实际运行支付的小程序 AppID，并完成微信侧所需的支付开通与商户关联 |
| stera smart one 应用 | 由 stera smart one 确认已配置微信支付 V3、小程序支付渠道及对应的小程序 AppID |
| API 密钥 | 应用的 Secret Key，仅保存在商户后端 |
| 小程序登录 | 商户后端具备通过微信登录凭证取得当前用户 openid 的能力 |
| 业务后端 | 创建订单、确定金额、调用 API、保存业务订单与 Charge ID 的对应关系 |
| 支付结果接收 | 可接收 HTTPS Webhook 的后端地址，并配置 Webhook 签名密钥 |

微信小程序 AppID 与 stera smart one 应用 ID 是不同标识。创建支付时无需在请求体传入微信 AppID，stera smart one 使用渠道中预先配置的 AppID。`extra.openid` 必须属于该小程序，不能使用另一个小程序或公众号取得的 openid，也不能用 unionid 替代。

商户不需要自行请求微信支付下单接口，也不需要自行生成 `paySign`。微信支付下单、支付签名和微信支付回调由 stera smart one 处理。

## 2. 整体流程

<EMermaid chart={`

    participant B as 商户后端
    participant E as elepay
    participant W as 微信支付

    M->>B: 提交 code，建立业务登录态
    B->>B: code2Session 取得 openid
    M->>B: 请求支付业务订单
    B->>E: POST /charges，携带 extra.openid
    E->>W: V3 小程序下单
    W-->>E: prepay_id
    E-->>B: Charge 与 credential
    B-->>M: chargeId 与支付参数
    M->>W: wx.requestPayment
    W-->>M: 客户端支付结果
    W->>E: 异步支付通知

    B->>B: 核对订单并幂等更新付款状态

客户端回调和服务端通知的到达顺序不固定。小程序显示的最终支付结果，应来自商户后端确认的状态。

## 3. 获取用户 openid

1. 小程序通过 `wx.login()` 取得临时 `code`。
2. 将 `code` 发送给商户自己的登录接口。
3. 商户后端使用该小程序的 AppID、AppSecret 和 `code` 调用微信 `code2Session`。
4. 将返回的 openid 绑定到商户业务登录态，下单时从登录态读取。

后端调用形式：

```http
GET https://api.weixin.qq.com/sns/jscode2session?appid=MINI_APP_ID&secret=MINI_APP_SECRET&js_code=LOGIN_CODE&grant_type=authorization_code
```

商户后端需要检查微信返回的错误，不能在 openid 缺失时继续下单。

<Callout type="warn">
AppSecret 和 `session_key` 不应下发到小程序。stera smart one 下单接口接收的是 `openid`，不接收微信登录 `code`。
</Callout>

微信接口定义参见 [code2Session 官方文档](https://developers.weixin.qq.com/miniprogram/dev/server/API/user-login/api_code2session.html)。

## 4. 商户后端创建支付

### 4.1 地址与认证

```http
POST https://api.elepay.io/charges
Authorization: Bearer <ELEPAY_SECRET_KEY>
Content-Type: application/json
```

API 必须从商户后端调用，不能把 Secret Key 放入小程序。也可使用 Basic 认证，将 Secret Key 作为用户名，**密码必须为空**（即 `sk_xxx:` 的 Base64）—— 密码段非空会直接返回 401。详见 [API 指南](/guides/api-guide)。

V3 版本由渠道配置选择，请求中不需要增加 `version` 字段。

### 4.2 请求参数

{/* prettier-ignore */}
| 字段 | 要求 | 说明 |
|---|---|---|
| `amount` | 必填 | 整数，JPY 以日元为单位；`100` 表示 100 日元。金额由商户后端根据订单计算 |
| `currency` | 建议明确填写 | 省略时默认 `JPY` |
| `paymentMethod` | 必填 | 固定 `wechatpay` |
| `resource` | 必填 | 固定 `mini` |
| `orderNo` | 必填 | 商户侧支付订单号，最长 50 字符，用于业务关联 |
| `extra.openid` | 必填 | 当前付款用户在对应小程序下的 openid |
| `capture` | 可省略 | 默认 `true`；普通微信支付使用 `true` |
| `description` | 可选 | 订单说明，最长 1024 字符；建议使用能识别商品或服务的简短文字 |
| `metadata` | 可选 | 商户自定义元数据 |

`orderNo` 的字符集没有约束，但支付渠道侧仍可能拒绝特殊字符，建议使用字母、数字与连字符。完整定义见 [Create charge](/openapi/charge/createCharge)；`extra` 各字段见[支付 Extra 信息设置](/guides/extra-setting)。

<Callout type="warn">
**本流程不要传入 `customerId` 与 `sourceId`。** 传入 `sourceId` 会切换到[免密支付流程](/cases/wechatpay-mini-v3-recurring)，与本指南的调起方式完全不同。
</Callout>

示例：

```bash
curl 'https://api.elepay.io/charges' \
  -H "Authorization: Bearer ${ELEPAY_SECRET_KEY}" \
  -H 'Content-Type: application/json' \
  --data '{
    "amount": 100,
    "currency": "JPY",
    "paymentMethod": "wechatpay",
    "resource": "mini",
    "orderNo": "MINI-20260915-0001",
    "description": "商品订单",
    "capture": true,
    "extra": {
      "openid": "OPENID_FROM_MERCHANT_SESSION"
    }
  }'
```

创建成功返回 HTTP `201`。商户应立即保存 `id`（Charge ID）与业务订单的关联。**创建成功表示取得了支付对象，不表示用户已付款。**

### 4.3 解析支付凭证

响应格式示例（仅展示相关字段，标识和签名为占位值）：

```json
{
  "id": "ch_xxxxxxxxxxxxxxxxxxxxxxx",
  "object": "charge",
  "liveMode": true,
  "orderNo": "MINI-20260915-0001",
  "amount": 100,
  "currency": "JPY",
  "status": "pending",
  "credential": "{\"provider\":\"wechatpay\",\"payload\":\"{\\\"appId\\\":\\\"MINI_APP_ID\\\",\\\"timeStamp\\\":\\\"1700000000\\\",\\\"nonceStr\\\":\\\"NONCE\\\",\\\"package\\\":\\\"prepay_id=PREPAY_ID\\\",\\\"signType\\\":\\\"RSA\\\",\\\"paySign\\\":\\\"PAY_SIGN\\\"}\"}"
}
```

正式模式下 `credential` 是明文的**两层 JSON 字符串，需要解析两次**：外层解出 `payload`，`payload` 本身仍是字符串，再解一次才是支付参数。无需 SDK 解密。

商户后端可按以下方式提取参数，再返回给自己的小程序：

```javascript
function buildMiniPaymentResponse(charge, expectedMiniAppId) {
  const credential = JSON.parse(charge.credential);
  const payment = JSON.parse(credential.payload);
  const fields = ['appId', 'timeStamp', 'nonceStr', 'package', 'signType', 'paySign'];
  if (fields.some((field) => typeof payment[field] !== 'string' || !payment[field])) {
    throw new Error('支付参数不完整');
  }
  if (payment.appId !== expectedMiniAppId || payment.signType !== 'RSA') {
    throw new Error('小程序 AppID 或签名类型不匹配，请联系技术支持');
  }
  if (!payment.package.startsWith('prepay_id=') || payment.package === 'prepay_id=') {
    throw new Error('预支付标识无效');
  }
  return { chargeId: charge.id, payment };
}
```

支付参数应原样使用，不要修改时间戳、随机串、package 或签名。若参数缺失、AppID 不匹配或签名类型不是 `RSA`，请联系技术支持。

<Callout type="warn">
**测试模式的 credential 格式不同。** 测试模式返回的是**加密字符串**，解密后是指向模拟支付页面的跳转凭证（`{"provider":"wechatpay","redirectUrl":"…"}`），**不含 `payload`、也不含任何微信支付参数**。对它直接 `JSON.parse` 会失败。测试模式无法用于小程序调起支付，详见第 8 节。
</Callout>

## 5. 小程序调起支付

### 5.1 支付参数处理

本流程无需引入 stera smart one 前端 JavaScript SDK。正式模式下（`liveMode=true`、`resource=mini`、不带 `sourceId`），按上一节解析支付参数，再调用小程序原生接口 `wx.requestPayment`。

### 5.2 调用示例

以下 `payment` 来自商户后端返回，`refreshOrderStatus` 和 `showPaymentMessage` 是由商户实现的业务函数：

```javascript
function startPayment(payment, refreshOrderStatus, showPaymentMessage) {
  const miniAppId = wx.getAccountInfoSync().miniProgram.appId;
  if (payment.appId !== miniAppId || payment.signType !== 'RSA') {
    showPaymentMessage('支付配置异常，请联系客服');
    return;
  }

  wx.requestPayment({
    timeStamp: payment.timeStamp,
    nonceStr: payment.nonceStr,
    package: payment.package,
    signType: payment.signType,
    paySign: payment.paySign,
    success() {
      showPaymentMessage('正在确认支付结果');
    },
    fail(error) {
      showPaymentMessage(
        error.errMsg === 'requestPayment:fail cancel'
          ? '已取消支付'
          : '支付未完成，正在确认订单状态'
      );
    },
    complete() {
      refreshOrderStatus();
    }
  });
}
```

`appId` 用于核对当前小程序身份，不作为 `wx.requestPayment` 的调用字段传入。**微信会校验下单时使用的 AppID 与调起支付的小程序是否一致**，两者不同会直接失败 —— 这正是上面那段校验要提前拦住的情况。V3 调起支付的 `signType` 固定为 `RSA`，签名由 stera smart one 生成。参见[微信官方小程序调起支付说明](https://pay.wechatpay.cn/doc/v3/merchant/4012791898)。

<Callout type="warn">
`success` 只用于触发结果确认，**不直接发货**；取消或客户端报错后也应查询后端状态。用户关闭小程序时，商户后端仍应独立接收支付结果。
</Callout>

## 6. 确认最终支付结果

### 6.1 接收 Webhook

在 stera smart one 中配置商户后端的 Webhook 地址、签名密钥和 `charge.succeeded` 事件订阅。

微信支付先通知 stera smart one，再由 stera smart one 通知商户。商户不应将自己的通知 URL 填入小程序 `extra`，也无需实现微信支付回调的解密协议。

支付成功通知示例（仅展示相关字段）：

```json
{
  "id": "EVENT_ID",
  "object": "event",
  "liveMode": true,
  "type": "charge.succeeded",
  "createTime": 1700000000000,
  "data": {
    "object": {
      "id": "ch_xxxxxxxxxxxxxxxxxxxxxxx",
      "orderNo": "MINI-20260915-0001",
      "amount": 100,
      "currency": "JPY",
      "status": "captured"
    }
  }
}
```

处理要求：

1. 使用原始 HTTP 请求体校验 `elepay-Signature`，不要先解析再重新序列化后验签。**HTTP 头名大小写不敏感**，请使用框架提供的不区分大小写的取值方式，不要按字面量精确匹配。
2. 签名头形式为 `t=<秒级时间戳>,sign=<十六进制签名>`；以 Webhook 签名密钥对 `时间戳 + "." + 原始请求体` 计算 HMAC-SHA256，并进行**恒定时间比较**。签名密钥在管理后台的 Webhook 详情页查看或重新生成，**不是 API Secret Key**。
3. **时间容差默认为 300 秒**（官方 Java SDK `Webhook.verifyHeader` 的默认值），超出范围的请求应拒绝，以防重放。
4. **同一个头可能携带多个 `sign=` 值**（密钥轮换期间），命中任意一个即视为通过。只解析第一个会在轮换期误拒。
5. 核对事件类型、Charge ID、业务订单号、金额、币种、正式／测试模式及 `status`。
6. 成功处理后返回 HTTP `2xx`。**失败时必须返回 4xx 或 5xx**，否则不会触发重试。
7. 重试策略：投递失败后按 **5 秒 / 15 秒 / 1 分钟 / 10 分钟 / 10 分钟** 的间隔重试，**重试 5 次（首次投递之外），累计投递 6 次，约 21 分钟后放弃**（平台既定值，不支持按商户单独配置）。**注意第二次投递最快在 5 秒后到达**，幂等窗口不要按分钟级设计。此后需依靠主动查询与对账补齐。
8. 对事件 ID 去重，并在业务订单层保证付款确认、发货只执行一次；应能处理重复与延迟到达的通知。
9. 收到未识别的 `type` 时返回 `2xx` 并忽略，**不要当作成功**。

Webhook 的配置与验证详见 [Webhook 文档](/guides/webhook)。

### 6.2 主动查询

商户后端可以使用同一应用、同一模式的 Secret Key 查询：

```bash
curl "https://api.elepay.io/charges/${CHARGE_ID}" \
  -H "Authorization: Bearer ${ELEPAY_SECRET_KEY}"
```

{/* prettier-ignore */}
| `status` | 业务处理 |
|---|---|
| `captured` | 已付款。核对金额等订单信息后确认业务订单 |
| `pending` | 未支付。显示确认中，稍后查询 |
| `waiting` | 等待支付（信息已输入）。显示确认中，稍后查询 |
| `notified` | 支付准备中（已通知）。显示确认中，稍后查询 |
| `uncaptured` | 已授权未确认。仅在 `capture=false` 时出现，本流程不会遇到 |
| `amount_mismatch` | **金额不一致，不可视为付款成功**，不得发货，须人工核查 |
| `failed` | 支付失败。根据业务规则允许重新发起 |
| `revoked` | 已撤销。根据业务规则允许重新发起 |
| `partially_refunded` | 已部分退款。按售后逻辑处理，不能当作新的付款成功 |
| `refunded` | 已退款。按售后逻辑处理，不能当作新的付款成功 |

查询返回的是当前状态，不能假定每次查询都会实时向微信查单。建议商户后端采用**有限次数、逐步延长间隔**的查询，并继续依靠 Webhook 完成最终确认。完整定义见 [Retrieve charge](/openapi/charge/retrieveCharge)。

小程序只查询商户自己的业务接口；商户后端必须验证当前登录用户有权查看该订单。

## 7. 异常处理

{/* prettier-ignore */}
| 情况 | 处理方法 |
|---|---|
| 缺少 `extra.openid` | 先完成微信登录，在后端绑定有效 openid 再下单 |
| AppID 或 openid 不匹配 | 核对运行的小程序、换取 openid 的 AppID、渠道配置的小程序 AppID 是否一致 |
| 支付参数或签名错误 | 核对 AppID，确认参数完整且未被修改；仍有问题时向技术支持提供 Charge ID 和错误信息 |
| `signType` 不是 `RSA` | 不要自行改写。向技术支持提供 Charge ID |
| 创建支付请求超时 | 先通过已保存的 Charge ID 查询；未取得 ID 时通过 Charge 列表核对 `orderNo` 或联系支持确认，**不要直接创建另一笔支付** |
| 重复订单号 | `orderNo` 不是可安全重放的幂等键。先查询已创建的支付并核实状态 |
| 用户取消或重复点击 | 防止同一订单并发创建支付；重试前先确认原支付状态 |
| 前端成功但后端尚未成功 | 显示确认中，等待通知或查询结果，**避免立即发货** |
| 状态为 `amount_mismatch` | 停止发货，人工核查金额来源 |
| 接口返回错误 | 只依据响应中的 `errorCode` 判别，不要匹配 `message` 文案。详见附录 |

## 8. 联调说明

<Callout type="warn">
**测试模式不能用于小程序调起支付。** 测试模式返回的是加密的模拟支付跳转凭证，既不能两层 `JSON.parse`，也不含 `wx.requestPayment` 所需的任何字段。

**Webhook V2 在测试模式下不投递任何事件。** 若需要在测试模式验证通知链路与幂等处理，请使用 V1 版本的 Webhook。
</Callout>

**真机调起支付及付款结果通知必须通过正式模式的小额支付验证。** 真实联调前由 stera smart one 确认正式渠道可用。

联调至少覆盖：

- 正式模式真实小额支付成功，核对 `status=captured`
- 用户取消支付
- 网络中断后恢复查询
- 重复点击同一订单
- 重复通知、签名不正确的通知
- 用户退出小程序后仍能确认付款
- 通知重试耗尽后，靠主动查询补齐状态

## 9. 接入完成标准

- 小程序 AppID、用户 openid 与渠道配置一致。
- 后端能创建支付、保存 Charge ID 并正确解析两层 JSON 凭证。
- 实际返回 `signType=RSA` 的支付参数，真机能够完成一次小额支付。
- 商户后端通过可信通知或查询确认 `captured`，业务订单仅处理一次。
- `amount_mismatch` 等非成功状态不会被误判为付款成功。
- 取消、超时、重复通知均不会造成重复支付或重复发货。

## 附录：错误响应

所有接口失败时返回统一结构（值为 `null` 的字段不出现）：

```json
{
  "requestId": "req_xxxxxxxxxxxxxxxxxxxxxxx",
  "errorCode": "M002003",
  "message": "要求されたリソースは存在しません。",
  "parameterName": "orderNo",
  "providerError": {
    "providerKey": "wechatpay",
    "code": "PROVIDER_ERROR_CODE",
    "message": "provider message"
  }
}
```

{/* prettier-ignore */}
| 字段 | 说明 |
|---|---|
| `requestId` | 请求标识。联系技术支持时请提供 |
| `errorCode` | **判别错误的唯一依据** |
| `message` | 面向人的提示文案，**请不要用于程序判断** |
| `parameterName` | 参数错误时指出具体字段 |
| `providerError` | 支付渠道返回的原始错误，排查时有用 |

三条要求：

1. **只认 `errorCode`。** 响应中还有一个 `code` 字段（形如 `9_xx_xx_10113`）**已废弃**，不要依赖。
2. **`message` 默认返回日语。** 需要其他语言请在请求头带 `Accept-Language`，支持 `ja` / `en` / `zh-CN` / `zh-TW`。
3. **`message` 来自服务端文案词典，内容可能调整**，请不要对它做字符串匹配。

错误码清单参见[错误码文档](/get-started/error-code)。
