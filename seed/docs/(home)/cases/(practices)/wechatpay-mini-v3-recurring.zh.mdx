**免密支付**：用户在微信小程序内签约一次，之后商户后端即可直接发起扣款，无需用户逐笔确认。适用于定期配送、订阅制、按量计费等需要重复扣款的业务。

<Callout type="warn">
使用本指南前，请联系 stera smart one 开通微信小程序免密支付并确认应用具备联调条件。代扣模板（plan）需单独申请开通。
</Callout>

## 1. 接入前准备

{/* prettier-ignore */}
| 项目 | 商户需要准备的内容 |
|---|---|
| 微信小程序 | 实际运行支付的小程序 AppID，并完成微信侧所需的支付开通与商户关联 |
| stera smart one 应用 | 由 stera smart one 确认已配置微信支付 V3、小程序渠道及对应的小程序 AppID |
| 免密支付开通 | 由 stera smart one 配置代扣模板（plan） |
| API 密钥 | 应用的 Secret Key，仅保存在商户后端 |
| 小程序登录 | 商户后端具备通过微信登录凭证取得当前用户 openid 的能力 |
| 业务后端 | 管理用户与 Customer / Source 的对应关系，发起扣款并记录 Charge ID |
| 支付结果接收 | 可接收 HTTPS Webhook 的后端地址，并配置 Webhook 签名密钥 |

微信小程序 AppID 与 stera smart one 应用 ID 是不同标识。创建 Source 与扣款时都无需在请求体传入微信 AppID，stera smart one 使用渠道中预先配置的 AppID。`extra.openid` 必须属于该小程序，不能使用另一个小程序或公众号取得的 openid，也不能用 unionid 替代。

商户不需要自行请求微信支付的签约或代扣接口，也不需要自行生成签名。微信侧的签约、扣款与回调均由 stera smart one 处理。

## 2. 整体流程

免密支付分为两个阶段：**签约**（一次性）与**扣款**（可重复多次）。

<EMermaid chart={`
sequenceDiagram
    participant M as 微信小程序
    participant B as 商户后端
    participant E as elepay
    participant S as 微信签约小程序
    participant W as 微信支付
    Note over M,W: 阶段一 签约（每个用户一次）
    M->>M: wx.login 获取 code
    M->>B: 提交 code，建立业务登录态
    B->>B: code2Session 取得 openid
    B->>E: POST /customers
    E-->>B: Customer ID
    B->>E: POST /customers/{id}/sources（extra.openid）
    E->>W: 预签约
    W-->>E: 签约会话标识
    E-->>B: Source 对象（status=pending，含 credential）
    B-->>M: 从 credential 解出的 sessionId
    M->>S: wx.navigateToMiniProgram（携带 sessionId）
    S-->>M: 用户完成签约并返回
    W->>E: 签约结果通知
    E->>B: source.activated Webhook
    Note over M,W: 阶段二 扣款（可重复）
    B->>E: POST /charges（customerId + sourceId）
    E->>W: 免密扣款
    W-->>E: 扣款成功
    E-->>B: Charge（status=captured，同步返回）
`} />

签约完成前无法扣款。签约完成后，扣款完全由商户后端发起，小程序不参与。

Customer 与 Source 的通用说明见[创建一个顾客并邀请绑卡](/cases/customer)。

## 3. 获取用户 openid

1. 小程序通过 `wx.login()` 取得临时 `code`。
2. 将 `code` 发送给商户自己的登录接口。
3. 商户后端使用该小程序的 AppID、AppSecret 和 `code` 调用微信 `code2Session`。
4. 将返回的 openid 绑定到商户业务登录态，创建 Source 时从登录态读取。

后端调用形式：

```http
GET https://api.weixin.qq.com/sns/jscode2session?appid=MINI_APP_ID&secret=MINI_APP_SECRET&js_code=LOGIN_CODE&grant_type=authorization_code
```

商户后端需要检查微信返回的错误，不能在 openid 缺失时继续创建 Source。

<Callout type="warn">
AppSecret 和 `session_key` 不应下发到小程序。stera smart one 接口接收的是 `openid`，不接收微信登录 `code`。
</Callout>

微信接口定义参见 [code2Session 官方文档](https://developers.weixin.qq.com/miniprogram/dev/server/API/user-login/api_code2session.html)。

## 4. 签约

### 4.1 地址与认证

```http
POST https://api.elepay.io/customers
Authorization: Bearer <ELEPAY_SECRET_KEY>
Content-Type: application/json
```

API 必须从商户后端调用，不能把 Secret Key 放入小程序。也可使用 Basic 认证，将 Secret Key 作为用户名，**密码必须为空**（即 `sk_xxx:` 的 Base64）—— 密码段非空会直接返回 401。详见 [API 指南](/guides/api-guide)。

### 4.2 创建 Customer

Source 挂在 Customer 之下，因此先创建 Customer。

```bash
curl 'https://api.elepay.io/customers' \
  -H "Authorization: Bearer ${ELEPAY_SECRET_KEY}" \
  -H 'Content-Type: application/json' \
  --data '{ "metadata": { "userId": "YOUR_USER_ID" } }'
```

请求字段全部可选，可按需传入 `name` / `email` / `phone` / `description` / `remark` / `metadata`。完整定义见 [Create customer](/openapi/customer/createCustomer)。

创建成功返回 `201`。**一个用户对应一个 Customer，请持久化保存 Customer ID 并复用**，不要每次签约都新建。同一 Customer 下可登记多个 Source。

### 4.3 创建 Source（发起签约）

```bash
curl "https://api.elepay.io/customers/${CUSTOMER_ID}/sources" \
  -H "Authorization: Bearer ${ELEPAY_SECRET_KEY}" \
  -H 'Content-Type: application/json' \
  --data '{
    "paymentMethod": "wechatpay",
    "resource": "mini",
    "description": "定期配送服务",
    "extra": { "openid": "OPENID_FROM_MERCHANT_SESSION" }
  }'
```

{/* prettier-ignore */}
| 字段 | 要求 | 说明 |
|---|---|---|
| `paymentMethod` | 必填 | 固定 `wechatpay` |
| `resource` | 必填 | 固定 `mini` |
| `extra.openid` | 必填 | 当前用户在对应小程序下的 openid。缺失返回参数错误 |
| `description` | 可选 | 会显示在用户的微信签约页面上，建议使用用户能识别的服务名称，最长 255 字符 |
| `metadata` | 可选 | 商户自定义元数据 |

完整定义见 [Create source](/openapi/customer/createSource)。创建成功返回 `201`，此时 Source 的 `status` 为 `pending`（未认证），**尚不能用于扣款**。

### 4.4 解析 credential，取出 sessionId

响应中的 `credential` 是**两层 JSON 字符串，需要解析两次**：外层解出 `payload`，`payload` 本身仍是字符串，再解一次才是签约参数。

```json
{
  "object": "source",
  "id": "src_xxxxxxxxxxxxxxxxxxxxxxx",
  "customerId": "cus_xxxxxxxxxxxxxxxxxxxxxxx",
  "liveMode": true,
  "paymentMethod": "wechatpay",
  "resource": "mini",
  "status": "pending",
  "credential": "{\"provider\":\"wechatpay\",\"payload\":\"{\\\"session_id\\\":\\\"SESSION_ID\\\"}\"}"
}
```

商户后端提取参数后返回给自己的小程序：

```javascript
function buildSigningResponse(source) {
  const credential = JSON.parse(source.credential);
  const payload = JSON.parse(credential.payload);
  if (typeof payload.session_id !== 'string' || !payload.session_id) {
    throw new Error('签约会话标识缺失');
  }
  return { sourceId: source.id, sessionId: payload.session_id };
}
```

只取 `session_id` 即可，不要依赖 `payload` 中的其他字段。**保存 Source ID 与业务用户的对应关系**，后续扣款、查询、解约都以它为准。

## 5. 小程序调起签约

<Callout>
本流程**不使用 `wx.requestPayment`**，也不需要引入 stera smart one 前端 SDK。微信的签约由一个独立的小程序承载，用 `wx.navigateToMiniProgram` 跳转过去。
</Callout>

```javascript
function startSigning(sessionId, refreshSigningStatus, showMessage) {
  wx.navigateToMiniProgram({
    appId: 'wxbd687630cd02ce1d',
    path: `pages/Oversea/walletSelect?sessionId=${sessionId}`,
    extraData: {},
    fail() {
      showMessage('无法打开签约页面，请稍后重试');
    },
    complete() {
      refreshSigningStatus();
    }
  });
}
```

`appId` 为微信签约小程序的固定值，不要改写。

<Callout type="warn">
**跳转目标不需要在 `app.json` 中声明。** 微信现行的 app.json 配置参考中已没有 `navigateToMiniProgramAppIdList` 字段；其中仍有的 `embeddedAppIdList` 是给 `wx.openEmbeddedMiniProgram`（半屏打开）用的，不是同一个接口。请不要为本流程添加该配置，但仍需实现 `fail` 回调处理跳转失败。
</Callout>

用户完成签约后会返回你的小程序，此时可读 `res.referrerInfo`：

```javascript
App({
  onShow(options) {
    const extraData = options.referrerInfo && options.referrerInfo.extraData;
    // extraData.contractId 可能不存在，仅作为「用户走完了流程」的提示
    this.refreshSigningStatus();
  }
});
```

<Callout type="warn">
`extraData.contractId` **不可作为签约成功的判据**。该字段可能缺失，微信官方也要求以服务端结果为准。请以下一节的 Webhook 或主动查询确认。
</Callout>

签约参数应原样使用，不要修改 `sessionId`。参见[微信官方小程序签约说明](https://pay.weixin.qq.com/doc/global/v3/en/4012356572)。

## 6. 确认签约结果

### 6.1 接收 source.activated Webhook

在 stera smart one 中配置商户后端的 Webhook 地址、签名密钥，并订阅 `source.activated` 与 `source.inactivated` 事件。

```json
{
  "id": "EVENT_ID",
  "object": "event",
  "liveMode": true,
  "type": "source.activated",
  "createTime": 1700000000000,
  "data": {
    "object": {
      "id": "src_xxxxxxxxxxxxxxxxxxxxxxx",
      "customerId": "cus_xxxxxxxxxxxxxxxxxxxxxxx",
      "paymentMethod": "wechatpay",
      "resource": "mini",
      "status": "active"
    }
  }
}
```

收到该事件并核对 `status` 为 `active` 后，才能对该 Source 发起扣款。

<Callout type="warn">
**Webhook V2 在测试模式下不投递任何事件**，包括 `source.*` 与 `charge.*`。若需要在测试模式验证通知链路，请使用 V1 版本的 Webhook；否则测试模式下请改用主动查询确认状态。
</Callout>

Webhook 的验签与重试要求见第 8 节。

### 6.2 主动查询签约状态

```bash
curl "https://api.elepay.io/sources/${SOURCE_ID}/status" \
  -H "Authorization: Bearer ${ELEPAY_SECRET_KEY}"
```

```json
{ "id": "src_xxxxxxxxxxxxxxxxxxxxxxx", "appId": "app_xxxxxxxxxxxxxxxxxxxxxxx", "liveMode": true, "status": "active" }
```

**两个查询接口的选用**：

- [Retrieve source's status](/openapi/customer/retrieveSourceStatus) —— 只返回 `id` / `appId` / `liveMode` / `status` 四个字段，**Secret Key 与 Publishable Key 都可调用**。轮询签约状态用这个。
- [Retrieve source](/openapi/customer/retrieveSource) —— 返回完整 Source 对象，**仅 Secret Key 可调用**。需要 `extra`、`metadata` 等完整信息时用这个。

{/* prettier-ignore */}
| `status` | 含义与处理 |
|---|---|
| `pending` | 未认证。用户尚未完成签约，或正在进行中。显示「签约进行中」，稍后再查 |
| `active` | 已认证。可以发起扣款 |
| `failed` | 认证失败。引导用户重新签约 |
| `inactive` | 已认证但当前不可用（通常是已解约）。不能扣款，需重新签约 |
| `deleted` | 已删除或已失效。不能扣款 |

小程序只查询商户自己的业务接口；商户后端必须验证当前登录用户有权查看该 Source。

## 7. 扣款

### 7.1 发起扣款

```bash
curl 'https://api.elepay.io/charges' \
  -H "Authorization: Bearer ${ELEPAY_SECRET_KEY}" \
  -H 'Content-Type: application/json' \
  --data '{
    "amount": 460,
    "currency": "JPY",
    "paymentMethod": "wechatpay",
    "resource": "mini",
    "orderNo": "MINI-20260915-0001",
    "description": "9月配送料金",
    "customerId": "cus_xxxxxxxxxxxxxxxxxxxxxxx",
    "sourceId": "src_xxxxxxxxxxxxxxxxxxxxxxx"
  }'
```

{/* prettier-ignore */}
| 字段 | 要求 | 说明 |
|---|---|---|
| `amount` | 必填 | 整数，JPY 以日元为单位；`460` 表示 460 日元 |
| `currency` | 建议明确填写 | 省略时默认 `JPY` |
| `paymentMethod` | 必填 | 固定 `wechatpay` |
| `resource` | 必填 | 固定 `mini` |
| `orderNo` | 必填 | 商户侧支付订单号，最长 50 字符 |
| `customerId` | 必填 | 签约时创建的 Customer ID |
| `sourceId` | **必填** | 已 `active` 的 Source ID，请务必传入；缺失时不会按免密方式扣款 |
| `description` | 可选 | 订单说明，最长 1024 字符 |
| `metadata` | 可选 | 商户自定义元数据 |

`orderNo` 的字符集没有约束，但支付渠道侧仍可能拒绝特殊字符，建议使用字母、数字与连字符。完整定义见 [Create charge](/openapi/charge/createCharge)。

### 7.2 处理响应

**扣款是同步的。** 创建成功返回 `201`，且响应中 `status` 已经是 `captured`、`paid` 为 `true`：

```json
{
  "id": "ch_xxxxxxxxxxxxxxxxxxxxxxx",
  "object": "charge",
  "liveMode": true,
  "orderNo": "MINI-20260915-0001",
  "amount": 460,
  "currency": "JPY",
  "paid": true,
  "status": "captured",
  "voucherNo": "4200000000000000000000000000"
}
```

`voucherNo` 是微信侧的交易号，可用于对账。

**本流程没有客户端调起步骤。** `POST /charges` 返回即表示扣款已完成，不要调用任何 `wx.*` 支付接口。

<Callout type="warn">
**关于响应中的 `credential` 字段**：本流程下该字段**会出现且非空**，但内容无意义，请不要解析，也不要用它判断扣款结果。扣款是否成功只看响应中的 `status` 与 `paid`。
</Callout>

扣款失败时返回错误响应，请按第 9 节处理。

### 7.3 扣款成功通知

stera smart one 同时会发送 `charge.succeeded` Webhook，结构与其他支付方式一致：

```json
{
  "id": "EVENT_ID",
  "object": "event",
  "liveMode": true,
  "type": "charge.succeeded",
  "createTime": 1700000000000,
  "data": {
    "object": {
      "id": "ch_xxxxxxxxxxxxxxxxxxxxxxx",
      "orderNo": "MINI-20260915-0001",
      "amount": 460,
      "currency": "JPY",
      "status": "captured"
    }
  }
}
```

由于扣款结果在同步响应中已确定，该事件主要用于对账与幂等兜底。**业务上仍应对事件 ID 去重，保证同一笔订单只处理一次。**

## 8. Webhook 处理要求

1. 使用原始 HTTP 请求体校验 `elepay-Signature`，不要先解析再重新序列化后验签。**HTTP 头名大小写不敏感**，请使用框架提供的不区分大小写的取值方式，不要按字面量精确匹配。
2. 签名头形式为 `t=<秒级时间戳>,sign=<十六进制签名>`；以 Webhook 签名密钥对 `时间戳 + "." + 原始请求体` 计算 HMAC-SHA256，并进行**恒定时间比较**。签名密钥在管理后台的 Webhook 详情页查看或重新生成，**不是 API Secret Key**。
3. **时间容差默认为 300 秒**（官方 Java SDK `Webhook.verifyHeader` 的默认值），超出范围的请求应拒绝，以防重放。
4. **同一个头可能携带多个 `sign=` 值**（密钥轮换期间），命中任意一个即视为通过。只解析第一个会在轮换期误拒。
5. 成功处理后返回 HTTP `2xx`。**失败时必须返回 4xx 或 5xx**，否则不会触发重试。
6. 重试策略：投递失败后按 **5 秒 / 15 秒 / 1 分钟 / 10 分钟 / 10 分钟** 的间隔重试，**重试 5 次（首次投递之外），累计投递 6 次，约 21 分钟后放弃**（平台既定值，不支持按商户单独配置）。**注意第二次投递最快在 5 秒后到达**，幂等窗口不要按分钟级设计。此后需依靠主动查询与对账补齐。
7. 对事件 ID 去重，并在业务层保证同一事件只处理一次；应能处理重复与延迟到达的通知。
8. 收到未识别的 `type` 时返回 `2xx` 并忽略，不要当作成功。

Webhook 的配置与验证详见 [Webhook 文档](/guides/webhook)。

## 9. 合约失效与异常处理

### 9.1 合约会在商户不知情时失效

用户可以在微信侧自行解约。商户需订阅 `source.inactivated`，收到后立即停止对该 Source 的扣款：

```json
{
  "type": "source.inactivated",
  "data": { "object": { "id": "src_xxxxxxxxxxxxxxxxxxxxxxx", "status": "inactive" } }
}
```

此外，每次扣款前 stera smart one 都会校验合约状态。若合约已终止，扣款请求返回 **HTTP `400`**，`errorCode` 为 **`M002003`**。

`M002003` 是通用的「资源不存在」错误码（Customer 或 Source 不存在时也是它），消息文案不会提到合约。**判别方法**：扣款返回 `400` 且 `errorCode` 为 `M002003` 时，调用 `GET /sources/{sourceId}/status` 复核 —— `status` 不是 `active` 即为合约已失效。

<Callout type="warn">
这是业务终态，**不要当作临时错误重试** —— 应停止扣款、标记该 Source 不可用，并引导用户重新走一次签约流程。
</Callout>

### 9.2 常见情况

{/* prettier-ignore */}
| 情况 | 处理方法 |
|---|---|
| 缺少 `extra.openid` | 先完成微信登录，在后端绑定有效 openid 再创建 Source |
| AppID 或 openid 不匹配 | 核对运行的小程序、换取 openid 的 AppID、渠道配置的小程序 AppID 是否一致 |
| `wx.navigateToMiniProgram` 跳转失败 | 核对 `appId` 与 `sessionId` 是否完整未被改写，并确认小程序基础库版本。该接口不需要在 `app.json` 声明跳转目标 |
| Source 长期停留 `pending` | 用户未走完签约。可引导重新签约，重新创建 Source 即可 |
| 返回时没有 `extraData.contractId` | 属正常情况，不代表失败。以 Webhook 或主动查询为准 |
| 扣款返回 400 + `M002003` | 合约可能已被解除。按 9.1 复核 Source 状态，不要重试 |
| 扣款请求超时 | 先用已保存的 Charge ID 查询；未取得 ID 时通过 Charge 列表核对 `orderNo`，不要直接再扣一次 |
| 重复订单号 | `orderNo` 不是可安全重放的幂等键。先查询已创建的支付并核实状态 |
| 接口返回错误 | 只依据响应中的 `errorCode` 判别，不要匹配 `message` 文案。详见附录 |

### 9.3 主动解约

```bash
curl -X DELETE "https://api.elepay.io/customers/${CUSTOMER_ID}/sources/${SOURCE_ID}" \
  -H "Authorization: Bearer ${ELEPAY_SECRET_KEY}"
```

返回 `204` 表示已受理。解约后该 Source 不可再用于扣款，用户需重新签约。完整定义见 [Delete source](/openapi/customer/deleteSource)。

## 10. 联调说明

测试模式**可以走完签约与扣款的完整业务链路**：签约通过 stera smart one 返回的测试确认页完成，不会发起真实的微信签约；Source 确认为 `active` 后即可扣款，扣款同步返回 `captured`。

但测试模式有三点与正式模式不同，**不能替代正式模式验证**：

- Source 的 `credential` 形态不同，是加密的测试跳转凭证，**其中没有可用于 `wx.navigateToMiniProgram` 的会话标识**，小程序端的真实签约跳转无法在测试模式验证。
- 不产生真实扣款，微信侧没有对应交易。
- **Webhook V2 在测试模式不投递任何事件**（见 6.1）。

**真实微信签约与扣款仍需正式模式的小额验证。** 真实联调前由 stera smart one 确认正式渠道与代扣模板可用。联调至少覆盖：

- 完整签约一次并收到 `source.activated`
- 用户中途放弃签约（Source 停留 `pending`）
- 签约后扣款成功，核对 `status=captured` 与 `voucherNo`
- 用户在微信侧自行解约后再扣款，确认返回 400 + `M002003` 且业务停止扣款
- 商户主动解约并收到 `source.inactivated`
- 重复通知、签名不正确的通知
- 扣款请求超时后的查询与对账

## 11. 接入完成标准

- 小程序 AppID、用户 openid 与渠道配置一致。
- 后端能创建 Customer 与 Source，并正确解析两层 JSON 的 credential 取出会话标识。
- 小程序能跳转到签约小程序并返回，签约结果以服务端为准确认。
- 收到 `source.activated` 后能成功发起扣款，响应同步返回 `captured`。
- `source.inactivated` 与扣款时的合约失效错误均有处理，不会对失效合约持续扣款。
- 解约链路可用，Webhook 重复投递不会造成重复发货。

## 附录：错误响应

所有接口失败时返回统一结构（值为 `null` 的字段不出现）：

```json
{
  "requestId": "req_xxxxxxxxxxxxxxxxxxxxxxx",
  "errorCode": "M002003",
  "message": "要求されたリソースは存在しません。",
  "parameterName": "sourceId",
  "providerError": {
    "providerKey": "wechatpay",
    "code": "PROVIDER_ERROR_CODE",
    "message": "provider message"
  }
}
```

{/* prettier-ignore */}
| 字段 | 说明 |
|---|---|
| `requestId` | 请求标识。联系技术支持时请提供 |
| `errorCode` | **判别错误的唯一依据** |
| `message` | 面向人的提示文案，**请不要用于程序判断** |
| `parameterName` | 参数错误时指出具体字段 |
| `providerError` | 支付渠道返回的原始错误，排查时有用 |

三条要求：

1. **只认 `errorCode`。** 响应中还有一个 `code` 字段（形如 `9_xx_xx_10113`）**已废弃**，不要依赖。
2. **`message` 默认返回日语。** 需要其他语言请在请求头带 `Accept-Language`，支持 `ja` / `en` / `zh-CN` / `zh-TW`。
3. **`message` 来自服务端文案词典，内容可能调整**，请不要对它做字符串匹配。

错误码清单参见[错误码文档](/get-started/error-code)。
